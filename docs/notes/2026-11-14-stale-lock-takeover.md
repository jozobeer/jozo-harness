# stale な session lock を二人で引き取る

## 現象

`<log>.lock` の pid が死んでいるとき、次の書き手は lock を名前のまま unlink してから作り直していた。別のプロセスが stale と判断したあと、先に新しい lock を link して戻った側のファイルまで、その unlink は消す。消した側も自分の lock を作るので、両方が書き込みに入る。zstd のフレームが混ざるか、次の修復が切れた末尾を捨て、セッションのイベントが消える。

同じ手順を別プロセスで 100 ラウンド走らせると、2 プロセスで 1 回（ラウンド 22）両方が取得に成功した。lock に残った pid は後から作った側だった。空の lock を奪い合う既存のテストは、この順番を踏まない。

再現の条件は、書き込み中のプロセスが強制終了で lock を残し、そのあと二つのプロセスが同じログを開くことである。web と CLI が同じ session root を使う構成や、再起動と重なった open がそれに当たる。同一プロセスの二度目の open はメモリ上の holder カウントなので、この競合には入らない。

## 直し方

stale と判断した lock は名前で消さず、`<log>.lock.grave.<id>` へ rename してその inode を読み直す。pid が生きていれば元の名前へ戻す。死んでいれば grave を捨ててから新しい lock を link する。grave が残っているあいだは新しい lock を作らない。link した直後に、別の生きた pid の grave があれば、自分のレコードだけを外して grave を戻す。

## 確かめ方

Node 26.8.2、pnpm 12.14.0 で次を実行し、11 ファイル 75 テストが通った。

```sh
pnpm exec vp test packages/core/session-jsonl
```

stale lock を 4ms の隙間つきで 8 ラウンド、2 プロセスが奪い合うテストを含む。grave の回復と、勝者が放したあとに次のプロセスが lock を取れることも見ている。`vp lint`、`vp run typecheck`、doc gate、重複検出も通った。

アルゴリズム単体では、grave 方式を 4 プロセス・遅延ありで 80 ラウンド走らせ、勝者が 1 人、lock の pid が一致、保持中に grave が残らない、解放後の再取得が成功、だった。
